# 并发库存：修改前复现结果

时间：2026-09-11 23:08:24 America/Los_Angeles。
本轮只复现问题，未修改库存扣减实现，也未执行支付。

## 测试方式

1. 使用 http://127.0.0.1:8081 的 baseline 应用，通过注册接口创建 100 个不同用户并获得各自 token。
2. 核实这些用户确实写入 lastcall_eats_baseline 数据库。
3. 新建专用商品 listing 1009991，初始库存 10，已有订单 0。
4. 使用 100 个 Python 客户端线程，在同步屏障（Barrier）等待后统一放行，每人只 POST /api/orders 一次，无重试。
5. 客户端开始发送的时间跨度约 11.7 毫秒。它不等于服务器同时执行 100 个事务；操作系统、请求线程和数据库连接池仍会调度请求。
6. 全部请求返回后，用 SQL 直接核对该 listing 的库存、订单数、不同买家数，并检查服务器日志。

## 结果

| 指标 | 实际值 |
|---|---:|
| 初始库存 | 10 |
| HTTP 200 成功 | 17 |
| 数据库订单数 | 17 |
| 不同成功买家数 | 17 |
| 最终剩余库存 | 0 |
| HTTP 400 商品不可用 | 25 |
| HTTP 500 内部错误 | 58 |

17 个订单均为 PENDING_PAYMENT。成功订单数超过初始库存，超卖（Overselling）已复现：多创建了 7 个订单。
订单数 + 剩余库存 = 17，不等于初始库存 10。库存为 0 并不能证明没有超卖。

同一秒服务器日志记录了 MySQL 错误 1213（Deadlock found），发生在更新 product_listing 时。
HTTP 500 不能归类为正常售罄拒绝；死锁（Deadlock）表示事务的锁等待发生循环，数据库中止其中的事务来解除等待。
本实验没有采集 InnoDB 完整死锁图，因此不进一步断言具体锁等待关系。

## 复现与限制

在项目根目录、baseline 应用运行时执行：

```bash
python3 scripts/baseline/concurrent_order.py
```

每次运行都会新增 100 个用户和一个库存 10 的专用 listing，保留数据与报告，不自动清理。
结果随请求调度而变化，不保证每次恰好 17 单。该脚本是诊断工具，脚本退出成功不表示库存校验通过，需检查报告的 oversold 和 inventory_consistent。
它不是扣库存后人为注入创建订单失败的回滚测试；该验证留到修复阶段。
凭据和 token 未写入报告。原始结果见 result.json，服务端日志摘录见 server-errors.txt。

测试新增了一个可用 listing（最终售罄），历史的 10,000 条商品压测数据已不再是未修改的初始 fixture；后续性能比较要重新确认数据规模和筛选条件。
