## 发现与解释

1. 商品浏览目前全量读取 listing 后在 Java 里筛选；数据增多时返回内容也随之增大。
2. 代码为每条 listing 查询 template，并读取 merchant。9 条数据时约 13 次 SELECT/请求；10,000 条且模板不同时约 10,004 次。这与列表查询 + 每个模板查询 + 少量商家查询的 N+1 结构一致。计数来自共享 MySQL 的全局 Com_select 差值，属于近似证据，其他客户端可造成少量偏差。
3. 下一阶段应先将筛选与分页下推数据库，再消除逐条查询；按执行计划选择索引。缓存实验应建立在已优化查询的基础上。

## 限制与复现

这是每个工作负载单次、30 秒的本机实验，不是生产容量或最大并发声明。单 VU 一万条数据的样本量较少，P99 不稳定。应用、MySQL 与 k6 共用本机资源；没有人为限制应用 JVM 堆大小，没有连接池内部指标或独立压测机。
合成的 9,991 条 listing 各有不同模板，轮流关联 3 个商家，全部有库存；不包含热点分布或大规模商家数据。
数据量比较同时改变了响应大小；加入分页后，必须报告页大小，并把“用户获取一页的延迟”与“完整列表的延迟”区分开。
当前数据库已扩充到 10,000 条，不能直接重跑 EXPECTED_COUNT=9 的命令。小规模复现应使用另一个全新实例/数据库，不要执行原 seed.sql 覆盖现有库。
